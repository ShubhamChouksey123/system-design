## The problem

> Design a monitoring and alerting system like Datadog that can collect metrics from thousands of servers, detect anomalies, and send intelligent alerts.

A clarifying question early in the session correctly reframed this as a **SaaS product** (multiple external customers, not one internal company) — the right move, since it changes the estimation base and introduces multi-tenancy as a first-class concern. What the prompt is really testing, underneath "collect and alert": can you tell the difference between a **storage problem** (ingest and retain time-series data at scale) and a **continuous-computation problem** (evaluate thousands of independent alert rules against live data with low latency)? Treating the second as "just query the first one on a schedule" is the trap this prompt is built to expose — the interviewer's own follow-up question walked directly at it.

## Terminology

| Term | Meaning |
|---|---|
| **Metric cardinality** | The number of distinct time series one metric name produces, once every tag/dimension combination (customer, service, host) is counted. Unbounded dimensions (a raw request ID as a tag) blow this up and overwhelm storage. |
| **Aggregation window** | How much data one evaluation of an alert rule covers — e.g. "the average over the last 5 minutes." This determines the *cost of one evaluation* (how much data gets aggregated), not how often that evaluation runs. |
| **Slide-by (evaluation cadence)** | How often a new evaluation result is produced, independent of the aggregation window's size — e.g. a 1-hour window can still be re-evaluated every minute if `slide_by = 1 minute`. **This, not the window size, is what drives evaluation frequency and therefore load** — real alerting products (e.g. NRQL-style alert conditions) model `aggregation_window` and `slide_by` as separate, independently configurable settings for exactly this reason. |
| **Alert deduplication** | Suppressing repeat notifications for a breach that is already open and unresolved, so one ongoing issue doesn't page an engineer every evaluation cycle. |
| **Baseline / historical comparison** | An alert condition that compares current data against a genuinely separate, disjoint historical period (e.g. "this hour vs. the same hour last week") — as opposed to a **rolling** condition, which only ever looks at a trailing window of recent data. |
| **Cold storage / sampling** | Moving data past a retention threshold (here, 7 days) to cheaper storage, and reducing its resolution, since dashboards and alerts rarely need full-fidelity history beyond a recent window. |

## Requirements & estimation

**What was produced** — functional: collect metrics/events from many source types; persist and query them; show time-series values on dashboards; detect anomalies and notify via Slack/PagerDuty on breach. Non-functional: scalable to a growing number of sources; highly available; real-time alert delivery; durable enough to compare against historical values; tolerant of **under 1% data loss**. A clarifying question ("internal tool or SaaS product?") correctly set the scope to a multi-tenant SaaS, with assumptions of **1-year retention**, full fidelity for the **last 7 days**, and sampling beyond that.

**Estimation, as produced:** 10,000 customers × 20 services × 50 metrics per 10-second interval ≈ **1M requests/sec**; each metric payload ≈ 100 bytes (name, timestamp, API key, value, account ID, infra tags) ≈ **100 MB/sec** ingest; 7-day full-fidelity storage computed on the canvas as **10 TB**. The throughput and bandwidth numbers are genuinely correct and internally consistent, and were reused to justify Kafka buffering and horizontal scaling of the collector.

**Gaps in the estimation:** the **storage figure itself has an arithmetic error** — the canvas's `100 × 60 × 60 × 24 = 10 TB` only multiplies the 100 MB/sec rate by the seconds in **one day** (`60 × 60 × 24 = 86,400`); it never multiplies by the stated 7-day retention window. Carried through correctly: `100 MB/sec × 86,400 sec/day ≈ 8.64 TB/day`, and `8.64 TB/day × 7 days ≈ 60.5 TB` — roughly **6× larger** than the number that was used to justify the cold-storage/sampling policy. The conclusion (cold storage + sampling is needed) still holds, and holds *more* strongly at the corrected number — but it's worth knowing the figure on the canvas undercounted its own 7-day retention requirement. Beyond that: no read-side number was derived — how many alert-rule evaluations per second does "thousands of customers × dozens of rules each" actually produce? That number is exactly what would have exposed the scheduled-polling design as non-viable before it was drawn. No cardinality estimate either (how many distinct time series does 10K customers × 20 services × 50 metric names actually produce?), and no explicit multi-tenancy/data-isolation requirement despite the SaaS framing being established upfront.

## The design I produced

![As-drawn architecture canvas. Metric sources send data via POST or gRPC to a metric collector that performs authentication, validation, and rate limiting, which publishes to Kafka, consumed by a metric enrichment service that performs aggregation and drop rules before writing to a time series datastore. Dashboards query through a query gateway with authentication, authorization, and rate limiting, into a query service that reads the time series datastore. An alerting system runs scheduled queries against the query service based on a configured rolling period, and on detecting an anomaly publishes a notification event to a second Kafka topic, consumed by a notification service that fetches user details from a user database and an integration key from an integration keys store, then calls PagerDuty, Slack, or email APIs, which notify the client engineer.](./diagrams/architecture.png)

- **Ingestion**: metric sources → metric collector (authN, payload validation, rate limiting) → Kafka, chosen explicitly as a buffer so the client-facing path never blocks on a database write.
- **Processing**: a metric enrichment service consumes Kafka, performs aggregation and drop-rule filtering, then writes to the time-series datastore.
- **Storage and query**: dashboards call a query gateway (authN/authZ/rate limiting) → a query service that reads the time-series datastore.
- **Alerting**: a separate alerting system runs **scheduled queries against the query service**, on a configurable rolling period (2 min, 5 min, etc.) per alert rule; on a threshold breach it publishes a notification event to a second Kafka topic.
- **Notification**: a notification service consumes that topic, resolves the destination (user DB + integration-keys store for PagerDuty/Slack/email credentials), builds a templated payload, and calls the external provider's API.
- **Scaling decisions during the walkthrough**: Kafka partitioned by `account_id`/customer ID (ordering per customer, parallelism across customers); the time-series datastore sharded by customer ID; the metric collector horizontally scaled behind a load balancer; alert deduplication by checking open/unresolved alert state before re-notifying.

## The ideal design

**The crux:** alert evaluation cannot be a periodic query against the storage tier for every rule — with thousands of customers each defining their own rules, that query volume alone would overwhelm the datastore long before any single rule's threshold logic becomes the bottleneck. The correct dimension to route on is **not window length** — a window's size only determines how much data one evaluation aggregates, not how often that evaluation runs. The real cost driver is **evaluation frequency (`slide_by`)** combined with whether a rule needs a genuinely disjoint historical comparison. A **rolling** rule (any window length — 1 minute or 1 hour — always looking at a trailing window of recent data) is cheapest as a continuously-maintained stream aggregate, re-evaluated at its own `slide_by` cadence entirely in memory. A **baseline/historical-comparison** rule (e.g. "this hour vs. the same hour last week") genuinely needs a value the live stream doesn't carry, but that baseline value itself changes slowly, so refreshing it on a low-frequency schedule (e.g. hourly) never approaches the query volume that made naive per-rule-per-minute polling a problem in the first place. The design routes each rule by **comparison type**, not window size.

| Baseline-refresh rate (after routing by comparison type, not window length) | ~90% of rules are rolling (any window, stream-evaluated, zero datastore queries) and ~10% ≈ 20,000 rules are baseline/historical-comparison, each refreshing its stored baseline value hourly rather than per-minute ≈ **20,000 / 3,600s ≈ ~5.6 queries/sec** | Confirms the datastore-facing load collapses to a trivial number once baseline values are refreshed on *their own* slow cadence — the key insight is that a historical baseline doesn't need to be re-fetched at the same frequency its *live* side is evaluated |

### Functional & non-functional requirements

**Functional** — ingest metrics/events from many source types per tenant; persist and query them on dashboards at any time range; let customers define threshold/anomaly alert rules; evaluate those rules continuously and notify (Slack/PagerDuty/email) within seconds of a sustained breach, deduplicated per open incident.

**Non-functional** — the **write path must never block on storage**; the **alert-evaluation path must be decoupled from the storage/query path** entirely; cardinality must be **bounded at ingest**; one tenant's traffic must not degrade another's (**noisy-neighbor isolation**); **sub-1% data loss is explicitly acceptable**, which licenses rejecting load under extreme pressure rather than queueing it indefinitely.

### Ideal architecture

![Architecture diagram for a multi-tenant metrics monitoring and alerting platform. ### Component walk-through

- **Ingestion never blocks on storage.** The Ingest Gateway authenticates, validates, and rate-limits **per tenant** before publishing to a durable, partitioned Kafka topic — the client-facing path ends there, exactly as reasoned correctly in the original session.
- **One enrichment stream, read once, forked twice.** The Enrichment Service is the single point that applies aggregation, drop rules, *and* the cardinality guard — after this point, both downstream paths see only clean, bounded-cardinality data.
- **The storage path optimizes for retention and flexible queries, not freshness.** Insert workers write into a time-series store sharded by `account_id`; a rollup compactor downsamples in the background; data older than 7 days tiers to cheaper cold storage — this is exactly the cold-storage-and-sampling strategy from the original session, now explicitly fed by its own write path rather than shared with alert evaluation.
- **Each alert rule is routed by *what kind of comparison it needs*, not by how big its window is.** The Alert Rule Router reads each rule's `comparison_type` — `rolling` or `baseline` — and sends it one of two ways. Window size and evaluation cadence (`aggregation_window`, `slide_by`) are **configuration passed to whichever evaluator owns the rule**, not the routing key itself; a 1-hour rolling window and a 1-minute rolling window both go to the same evaluator, they just configure different bucket sizes.
- **Rolling rules never touch the datastore, regardless of window size.** The Rolling-Window Evaluator consumes the *same* enrichment stream and maintains a continuously-updated, time-bucketed aggregate **per alert rule**, re-emitting a result at that rule's own `slide_by` cadence — a 1-hour window costs the same per-tick as a 1-minute window, because both are just summing a bounded number of in-memory buckets. This covers the large majority of rules (any threshold alert on recent/trailing data) and is what makes "thousands of customers × dozens of rules" a non-issue instead of a scaling crisis, no matter how those rules' windows are configured.
- **Baseline rules query the datastore, but only to refresh a slow-changing value — not on the rule's own evaluation cadence.** The Baseline Evaluator queries the Query Gateway on a schedule tied to how often the *baseline itself* meaningfully changes (e.g. hourly for a week-over-week comparison), which is completely decoupled from how often the rule's live side is checked. This is the honest answer for rules that genuinely need a disjoint historical data point the stream can't provide — and it's cheap specifically because a baseline value is refreshed rarely, not because its window happens to be "long."
- **Dedup happens before the Kafka hop, not after — for both evaluators.** Each evaluator checks the Alert State Store for an already-open breach *before* publishing — so a sustained issue produces one incident, not one event per evaluation tick, the same correct instinct the original session reached (just applied one step earlier in the pipeline, and shared by both paths).
- **Notification delivery is idempotent.** The Notification Service's call to PagerDuty/Slack/Email is keyed so a redelivered Kafka message cannot double-page an engineer — the explicit fix for the delivery-semantics gap the interviewer asked about only at the very end.

### Storage choices — which engine for which store

| Store | Category | Why this category, not another |
|---|---|---|
| Raw Metric Topic / Partitioned Write Topic / Alert Event Topic | **Durable log (Kafka)** | Absorbs a huge bursty write rate without blocking the client, and is replayable if a downstream consumer falls behind — the same durability-first ingestion pattern as [the write-ahead-log concept](../../concepts/08-distributed-systems/write-ahead-log-and-durable-ingestion.md). |
| `metric_point` (raw + rollups) | **Wide-column / columnar time-series store** | Access pattern is "scan a time range for one series," not point lookups — a column-oriented, time-partitioned engine compresses and scans far better than a general-purpose row store for this shape. |
| `window_state` | **In-memory KV, time-bucketed** | Needs O(1) increment/read per evaluation tick at massive concurrency, for any window size; ephemeral by design, rebuildable from the stream — the same pattern as [session 16](../16-session/README.md)'s trending-window state. |
| `baseline_value` | **In-memory KV with a long TTL, or a small cache table** | Tiny, read far more often (once per rule's `slide_by`) than written (once per `baseline_refresh_interval`) — a cache in front of the one-time-per-refresh datastore read, not a store that needs its own durability story. |
| `alert_state`, `alert_rule`, `user`, `integration_key` | **Relational (RDBMS)** | Small, structured rows with real relationships and low write frequency — a textbook relational fit; `alert_state`'s unique constraint is exactly why this one needs to be relational and not a cache. |
| Cold Storage | **Object storage** | Cheap, durable, infrequently read — exactly the access pattern of data past the 7-day full-fidelity window. |

### Design trade-offs

- **Route by comparison type (rolling vs. baseline), not by window size** — the single most important fix, and a correction of an earlier draft of this same design that routed by `window_duration`. Window length only determines how much data one evaluation touches; it says nothing about how often that evaluation runs. The real decision is whether a rule can be answered entirely from a trailing window of recent stream data (`rolling`, any size, any `slide_by`) or whether it needs a genuinely separate historical data point (`baseline`) — this is the axis that actually determines whether the datastore is involved at all.
- **Decouple a baseline's refresh rate from the rule's own evaluation cadence (`slide_by`)** — a week-over-week baseline doesn't change minute to minute, so the Baseline Evaluator refreshes its cached value on its own slow schedule (e.g. hourly) while the rule can still be *evaluated* against that cached value as frequently as its `slide_by` requires. Conflating "how often is this rule checked" with "how often does its historical reference point need updating" is exactly the mistake that made window length look like the relevant variable in the first place.
- **Reject load over queueing it indefinitely** — the session's own stated non-functional requirement (sub-1% data loss is acceptable) licenses this: under extreme load, reject at the Ingest Gateway rather than let an unbounded queue build latency everywhere downstream. This was reasoned correctly in the original session and carries over unchanged.
- **Cardinality rejected/sampled at ingest, over stored and discovered later** — a single tenant's misconfigured tag should degrade that tenant's own data, not the shared datastore's performance for everyone else.
- **Managed message-queue service over self-hosted Kafka** — a legitimate trade-off the original session raised: self-hosted Kafka's operational burden (the session's own stated top reliability concern) can be traded for a managed service's reduced feature surface and potential vendor lock-in; name both sides, not just the one being chosen.
- **Consistency, stated per path** — the storage/dashboard path is **AP** (a dashboard a few seconds stale is a non-event). The `alert_state` dedup constraint is the one place this design needs **CP**-like atomicity, so two evaluator replicas can't both open the same incident.

### Logging, Monitoring & Alerts

| Signal | Alert threshold | Why it matters |
|---|---|---|
| **Ingest consumer lag** | Lag growing, not draining | Enrichment is falling behind live traffic — both storage and alerting go stale together |
| **Cardinality-violation rate** | Sustained spike above baseline | Signals a misconfigured integration minting unbounded series — the exact failure mode the cardinality guard exists to contain |
| **Rolling-evaluator latency** (breach-to-notification) | p99 exceeding the product's advertised alerting SLA | The entire purpose of the stream-fed fork is speed; a regression here means it has failed its purpose |
| **Baseline-refresh query rate and staleness** | Query rate climbing faster than `rule count ÷ baseline_refresh_interval` predicts, or `last_refreshed_at` falling behind the configured interval | Signals the router is misclassifying rolling rules as baseline (inflating refresh load) or the refresh job itself is falling behind |
| **Rollup-compactor backlog** | Raw data older than N hours still unrolled | Long-range dashboard queries will scan raw data or miss it once retention on raw data expires |
| **Notification delivery failure rate**, per channel | Any sustained non-zero rate on a critical channel (PagerDuty) | An alert that fires internally but never reaches an engineer is equivalent to no alert at all |

## Takeaways to drill

1. **Window size and evaluation frequency are two different knobs — don't route on the one that doesn't actually drive load.** This tracker's own first pass at this design made exactly this mistake, routing rules by `window_duration` ("short window → stream, long window → poll"). The correct model: **aggregation window** (how much data one evaluation touches) and **slide-by** (how often a new evaluation runs) are independent — a 1-hour window re-evaluated every minute costs the same per tick as a 5-minute window on the same cadence. Real alerting products model these as separate settings for exactly this reason. Route instead on **comparison type**: a **rolling** rule (any window, any slide-by) is cheap as a stream-fed incremental aggregate; a **baseline/historical** rule needs one genuinely disjoint data point, refreshed on *its own* slow schedule, decoupled from how often the rule itself is checked. This generalizes the "fork the stream" lesson from [session 16](../16-session/README.md) — the dimension that decides "stream vs. query" is *what kind of answer the computation needs*, never how big a number happens to appear in the rule's configuration.
2. **"Intelligent alerts" implies more than a static threshold — say so even if you don't implement it.** Naming the trade-off (static thresholds vs. baseline/seasonality-aware detection) costs one sentence and directly answers what the prompt asked for.
3. **Cardinality control is a day-one requirement on any multi-tenant, dimensional-metric system**, not an afterthought — state the per-series limit and where it's enforced (at ingest, before storage or evaluation).
4. **"This is a SaaS product" is a commitment, not just a scoping answer** — once stated, tenant isolation (rate limits framed as noisy-neighbor protection, not just abuse protection) needs to show up somewhere in the design.
5. **State the delivery guarantee and idempotency before being asked.** At-least-once ingestion + an idempotent notification send is the same durability pattern as [the write-ahead-log concept](../../concepts/08-distributed-systems/write-ahead-log-and-durable-ingestion.md) — naming it proactively, rather than only when asked "what if Kafka goes down," is the senior signal.
6. **When the thread breaks, restart cleanly — don't narrate the confusion.** Communication was the lowest axis here, the same note this tracker gave after S10/S11 and again after S14: pause, re-anchor with "let me back up," and continue, rather than talking through a stalled answer.
7. **Once a component is named as critical, go one level under it — "how does this actually work?"** Anomaly detection was named as a requirement in the first minute and never opened back up; the senior move is to pick the *one* component the prompt is clearly built around and spend real time on its internals, not just its name on a box.
8. **Every design decision should name the alternative it rejected, not just the choice made.** "I chose Kafka over a managed queue because X, but the trade-off is Y" scores higher than naming Kafka alone — this showed up once here (the Kafka-vs-managed-queue question), and should be the default shape for every major choice, not a one-off.
9. **Budget time so design depth and scaling discussion aren't crowded out by a lengthy requirements/estimation opening.** A rough split for a ~45–50 minute round: Requirements ~5 min, Estimation ~5 min, Design + walkthrough ~25 min, Scale + trade-offs ~15 min. The opening sets up the design; it shouldn't consume the time the harder, higher-scoring back half needs.
10. **Re-derive a number from its own inputs before presenting it — don't trust a multiplication that "feels" done.** The 7-day storage figure here dropped the ×7 entirely (computing one day's volume and calling it the week's), and it went uncaught through the whole session. A quick sanity re-check — "does this number scale the way I just said it should?" — catches this class of error before it's said out loud.
