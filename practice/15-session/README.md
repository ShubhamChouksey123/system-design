# Session 15 — Property Search & Reservation System (hotel-booking style) · self-practiced

> A **self-practiced** design — the mock-interview platform didn't have a hotel-booking prompt, so this was worked solo, with no interviewer and no transcript. Framed **Airbnb-style**: each property is a single bookable unit, so at most one booking can hold any given night — there's no room-type/inventory-count layer, which simplifies the crux considerably. No mock-platform score exists, so this write-up skips the numeric scorecard and instead reviews the requirements, the design produced, and the schema directly against this repo's own recurring lessons. The design correctly *named* the crux upfront — "prevent double bookings" — but the double-booking guard it built (a Redis lock with no DB-level backstop, on a schema with a single `date` field) never actually closes the loop, and search runs completely disconnected from availability. Both are fixed below.

## The problem

> Design a cloud-native property platform handling listing, search, and booking concurrency. Prevent double bookings using a two-step API reservation (hold, then confirm post-payment). Sync database changes to a search index under 500ms. Handle asynchronous bulk updates of thousands of merchant properties without blocking real-time reads.

The crux isn't listing or paying for a property — it's that **two guests can attempt to reserve the same property for overlapping dates at the same instant**, and a naive read-then-write check loses that race under concurrency. Everything else (search, media, notifications) is a well-worn pattern this repo has already solved elsewhere; the reservation-write path is the one piece unique to this domain.

## Terminology

| Term | Meaning |
|---|---|
| **Room-night** | One property (or room type) for one calendar night — the atomic unit of inventory in a booking system. A 3-night stay consumes three room-nights. |
| **Inventory hold** | A temporary, time-boxed claim on a room-night placed at reservation time, before payment completes — must be released automatically if payment never happens. |
| **Two-phase booking (reserve / confirm)** | Splitting a booking into `POST /reserve` (places the hold, returns a price) and `POST /confirm` (called after payment succeeds, flips the hold into a real booking) — the pattern this session's requirements named but the architecture never fully wired. |
| **Overbooking** | Selling more room-nights than actually exist for a date — the failure mode the whole reservation-write path exists to prevent. |
| **Atomic conditional update** | A single `UPDATE … WHERE <guard>` that both checks and mutates in one database operation, so the check can't go stale between "read" and "write" — the same primitive this tracker's rate-limiter and auction sessions already established as the fix for a shared-state race. |

## Requirements & estimation

**Functional** — list/view a property; search by city; book a property for specific dates ("standard hotel days"); pay during booking; receive a booking-confirmation notification; admin/merchant can bulk-update thousands of properties at once.

**Non-functional** — writes consistent, durable, reliable; reads fast; highly available.

**Estimation produced** — 10M total users, 5M DAU, 100 requests/user/day, 100:1 read:write → ~5,000 QPS average (50 writes/sec); 100 cities × 200 properties/city = 20,000 properties, 20 media items/property × 20MB avg → 8TB total media storage.

**Gaps against this repo's own estimation conventions** ([back-of-the-envelope estimation](../../concepts/01-envelope-estimation/back-of-the-envelope-estimation.md)):

- **No `Peak ≈ 2× Average` applied** — the 5,000 QPS / 50 writes-per-sec figures are never doubled for peak, despite that being this repo's own stated convention.
- **No hot-key number** — the aggregate write QPS (50/sec) says nothing about contention on *one* popular property during a demand spike (a holiday weekend, a flash sale). This is [Recurring Action Item #1](../README.md#recurring-action-items) in this repo's own tracker — "size the hot key, not the aggregate" — and it's exactly the number that decides whether the reservation path needs gateway-level throttling per property.
- **No number ties to a decision.** None of the produced figures change an architectural choice; they're recorded but not used, which is the estimation gap this tracker calls out on 9 of its 14 prior sessions.

## The design I produced

![Architecture canvas for a property search and reservation system. A client, either a guest or a property owner and merchant, calls an API Gateway doing authentication, authorization, and rate limiting, which routes booking requests to a Booking Writer service and a Booking Reader service, property requests to a Property Reader service and a Property Write service, and media uploads to AWS S3 via a signed URL. The Booking Writer service adds a pending payment entry to a Bookings database writer instance, provides a price, and locks the property for a time, invalidates a Bookings cache on write, and informs a Payment service after a successful booking, which calls an external payment provider such as PayPal, receives webhook status updates, and notifies a Notification service that pushes to the client over server sent events. The Bookings database writer instance replicates to a Bookings database reader instance, which repopulates the Bookings cache on a cache miss. The Property Reader service fetches property data by id or by search from a Property cache, falling back to a Property database reader instance on a cache miss, while the Property Write service writes to a Property database writer instance and invalidates the Property cache on update. The Property database writer instance is read by a Debezium instance that reads the database's write ahead logs and converts them into change events consumed by an Event Listener Worker, which sends the data to AWS Elasticsearch for search. On the media side, uploads go to AWS S3 through a signed URL, an upload event listener worker publishes to a Kafka queue, a Breaker service chunks large media and creates a pipeline for each rendition, a Transcode Manager assigns tasks to a pool of transcode workers and informs the Property Write service once media is available, and an Upload worker uploads the final rendered files back to AWS S3, which the client reads through a CDN.](./diagrams/architecture.png)

- **Reader/writer split with caching** — Property and Bookings each get a writer instance, a replicated reader instance, and a cache-aside layer invalidated on write, falling back to the reader instance on a cache miss.
- **Booking write path** — `POST /book` → Booking Writer service adds a pending payment entry, prices the stay, and "locks the property for a time," then hands off to Payment service.
- **Payment** — Payment service calls an external provider (PayPal), receives status via webhook, and informs Booking service on success; Notification service then pushes a confirmation to the client over SSE.
- **Search sync** — Debezium reads the Property DB's WAL, an Event Listener Worker consumes the change events and writes them into AWS Elasticsearch, which the Property Reader service queries for search.
- **Media pipeline** — signed-S3-URL upload → Kafka → a Breaker service chunking large media → a Transcode Manager assigning work to a transcode-worker pool → an Upload worker writing renditions back to S3 → served through a CDN. This sub-system is genuinely well-designed and is kept unchanged in the Ideal Design below.

## What lost points — and the fix

| What the design missed | What a senior answer looks like | Study |
|---|---|---|
| **The double-booking guard has no durable backstop.** The requirements name a Redis distributed lock with a TTL hold, but the `Bookings` schema has a single `date` field with no unique constraint or range-exclusion — if the lock expires, is skipped, or a request retries, nothing in the database itself stops two bookings for the same night. | A distributed lock is a mutex, not a source of truth. Back it with a **unique constraint on `(property_id, stay_date)`** — since each property is a single bookable unit, that constraint alone rejects a second booking for the same night, no counter needed — so the database enforces the invariant even if the lock fails. | [Concurrency Control](../../concepts/08-distributed-systems/concurrency-control.md) |
| **`Bookings.date` doesn't model a stay.** A single date field can't represent a check-in/check-out range, and it's ambiguous whether one row means one night or one whole stay — a booking for a 3-night stay has nowhere unambiguous to live. | Model one row per **booked night** (`property_id`, `stay_date`), with a **unique constraint on the pair** — since each property is a single bookable unit (Airbnb-style, not multi-room-type), the constraint alone *is* the double-booking guard: a second `INSERT` for the same property/night simply fails. Wrap one `INSERT` per night of the stay in a single transaction so a partial overlap can't leave a half-booked stay. See the Ideal Design schema below. | [Databases — Fundamentals](../../concepts/05-databases-and-storage/databases-fundamentals.md) |
| **Search never checks availability.** The Property Reader service filters by city (via Elasticsearch) but never joins against Bookings — a guest can see, and attempt to book, a property that's already fully booked for their dates. | Wire search as two steps: candidate ids from the index (city/price), then a **live availability filter** against the booking-night table before returning results — the same "index for candidates, hydrate/verify from the source of truth" pattern already used for property details. | [Sharding & Partitioning](../../concepts/05-databases-and-storage/sharding-and-partitioning.md) |
| **No idempotency key on `/book` or `/pay`.** Both are retriable client calls with no dedup token in the schema, risking a duplicate booking or a double charge on retry. | Idempotency key on both the booking row and the payment row, checked before the write — a repeat action item in this repo since S03/S04. | [API Security](../../concepts/04-apis/api-security.md) |
| **The bulk-update requirement has no matching architecture.** "Admin can update thousands of properties at once" is named as a functional requirement, but Property Write service in the diagram only shows single-property writes — no batching, no async job, no throttled cache invalidation to avoid a thundering herd on `Property Cache`. | Give bulk updates their own async, chunked path with rate-limited (not synchronous, all-at-once) cache invalidation. | [Message Queue](../../concepts/07-messaging-and-events/message-queue.md) |
| **No monitoring/alerting named anywhere.** The requirements state a "sync under 500ms" SLA with no metric backing it, and there's no signal for lock contention, replication lag, or pipeline failure. | Name concrete, alertable signals — see Logging, Monitoring & Alerts in the Ideal Design. | [Observability](../../concepts/09-reliability-and-operations/observability.md) |

## The ideal design

**The crux:** two guests can race to reserve the same property for overlapping dates; since each property is a single bookable unit (Airbnb-style — no room types, no per-night unit counts), the fix is the **two-step reservation the problem statement itself asks for** — `POST /reserve` takes a **Redis distributed lock per night, TTL-bound to the hold window**, then `POST /confirm` finalizes after payment — with the lock backed by a **durable `(property_id, stay_date)` unique constraint** in the database, so correctness survives even if the lock is lost, skipped, or expires early. The lock buys latency (reject contention in Redis, never touch the DB under a hot-property spike); the constraint buys correctness (the actual, durable proof that a night is taken).

### Ideal estimation (decision-tied)

| Number | Value | Decision it forces |
|---|---|---|
| Steady throughput | 5M DAU × 100 req/day ÷ 86,400s ≈ **5,800 QPS avg**, ×2 → **~11,600 QPS peak** (100:1 read:write → ~58/sec avg writes, ~116/sec peak) | Confirms the read path (search/browse) needs aggressive caching; the write path is small enough that a single relational primary handles it comfortably |
| **Hot-property contention** | Assume the top 0.1% of 20,000 properties (~20 listings) see a 50× traffic spike during a holiday-weekend rush → **~50–100 concurrent reservation attempts/sec on one property** | Forces a **per-property soft throttle at the gateway** (e.g. queue/backoff past a threshold) so a flash-sale property doesn't thrash the DB with failed transactions — the aggregate write QPS alone never surfaces this; note the contention is even simpler to resolve than a counter-based model, since only the *first* concurrent `INSERT` for a given night can ever succeed |
| Booking-night calendar size | 20,000 properties × 730 days (rolling ±1yr window), and — unlike a per-room-type model — **only booked nights get a row** (an open night has no row at all), so real volume is closer to occupancy × 20,000 × 730; at, say, 50% average occupancy ≈ **~7.3M rows**, each a few dozen bytes ≈ **well under 1GB** | Confirms the table is trivially small for a normal relational store with a composite unique index — it does **not** need the in-memory single-writer treatment a matching engine's order book needs; a different medium is correct here because writes are orders of magnitude less frequent, and sparsity (only booked nights exist) keeps it small regardless of catalog growth |
| Booking retention | ~50,000 bookings/day × 365 ≈ 18M bookings/yr at ~200B/row ×3 replication ≈ **~11GB/yr** | Confirms the Booking DB doesn't need sharding for years — a single primary + read replicas is enough; revisit only once yearly volume changes by an order of magnitude |

### Functional & non-functional requirements (the ideal cut)

- **Functional** — search by city **and date range** (not city alone) returning only available listings; view property + room-type detail; two-phase reservation (`reserve` places a time-boxed hold, `confirm` finalizes after payment); pay for a reservation with an idempotent charge; auto-release an expired, unpaid hold; cancel a confirmed booking (release inventory, trigger refund); notify on confirmation/cancellation; owner/admin bulk-update thousands of listings without blocking reads; upload and serve transcoded property media.
- **Non-functional** — booking/payment writes are **strongly consistent and durable** (never double-book, never lose a paid reservation); search/browse reads are **fast and highly available**, tolerating a few seconds of staleness because the reservation step re-verifies availability live; the write and read paths are explicitly split **CP vs. AP**.

### Ideal architecture

![Architecture diagram for the ideal property search and reservation system. A client calls an API Gateway handling authentication, authorization, and rate limiting. A red write path has a Booking Service that, on a reserve request, first acquires a Redis distributed lock per night in the stay range with a TTL bound to the hold window, then, once every night's lock is held, runs one database transaction inserting a row for every night in the stay range into the Booking Night Calendar table, where a unique constraint on property and night rejects any night already taken, and inserts a booking row with status PENDING and an expiry time into a Booking Database Primary, which replicates to a Booking Database Read Replica and invalidates a Booking Cache on Redis; a Hold Expiry Reaper Job sweeps expired PENDING bookings, deletes their held night rows from the calendar table, and releases any lock that was not already released; the same Redis lock's own TTL is a backstop that auto expires it even if the reaper is delayed. A yellow payment path has a Payment Service that charges an External Payment Provider such as PayPal, receives a webhook with payment status, deduplicates by an idempotency key against a Payment Database, and on success tells the Booking Service to flip the booking from PENDING to BOOKED and release the night's Redis locks, which then calls a Notification Service that pushes a booking confirmed event to the client over server sent events. A purple property-write and search-sync path has a Bulk Update Worker consuming admin bulk update requests through a Kafka topic into a Property Write Service that performs chunked writes to a Property Database Primary and asynchronous rate limited cache invalidation; the Property Database Primary is read by Debezium via database write ahead logs into a Kafka CDC topic consumed by a Search Index Sync Worker that updates the Search Index. - **Availability check is a first-class step in search, not an afterthought.** The Search Service does candidate-id lookup by city/price *then* a live filter against the booking-night calendar *then* hydration — a property that's already booked for the requested dates never reaches the client.
- **`POST /reserve` is genuinely two-phase, matching the problem statement.** Step one: acquire a **Redis distributed lock per night** in the stay (`lock:{property_id}:{stay_date}`), TTL-bound to the hold window (e.g. 10 minutes) — if any night's lock is already held, fail fast without ever touching the database, which is exactly what shields a hot property from thrashing the DB during a spike. Step two, only once every night is locked: **one database transaction** `INSERT`s a `booking_night` row per night and the `booking` row (`status = PENDING`, `expires_at`). Because each property allows exactly one booking per night, the **unique constraint on `(property_id, stay_date)` is the durable backstop** — it's what still prevents a double booking even if the lock was lost, expired early, or skipped (a redeploy, a Redis failover, a retried request that never acquired the lock at all).
- **`POST /confirm` is the second phase, called after payment succeeds.** It flips the booking `PENDING → BOOKED` and releases that stay's Redis locks — at that point the durable `booking_night` rows are permanent proof of the booking, so the lock has done its job and can go.
- **The hold's expiry has two independent backstops, not one.** The Redis lock's own **TTL auto-expires it** even if nothing else runs; separately, a `Hold Expiry Reaper` job sweeps `PENDING` bookings past their DB-side `expires_at`, deletes the corresponding held-night rows, and releases the lock if it's somehow still held. Two independent expiry paths (Redis TTL, DB-driven reaper) mean a stuck hold can't survive either one failing alone.
- **Why keep the `booking_night` table at all, given the lock** — a distributed lock is fast but not durable: it can be lost on a Redis failover, misjudged on TTL, or simply never acquired by a buggy retry. Without a database-side constraint, that failure mode is a silent double booking. The lock and the table aren't redundant — the lock is the low-latency guard that keeps contention off the database; the table is the one thing that's actually true no matter what Redis does. This is also what avoids a **dual-write hazard**: the `booking_night` `INSERT` is the single write that makes a night "taken," never a second, independent system of record that could drift from it.
- **Bulk updates get their own async, chunked path** — a dedicated worker consuming from Kafka, writing to `Property DB` in batches, and invalidating the cache asynchronously and rate-limited, so a 10,000-property update can't thundering-herd the cache or block real-time reads.
- **The media pipeline is carried over unchanged** from the session's own design — it was already well-built.

### Booking flow walkthrough

A step-by-step trace of one reservation, from `POST /reserve` through `POST /confirm` — or an abandoned hold:

1. **Client calls `POST /reserve`** with `property_id`, `check_in`, `check_out`. The Booking Service expands the range into individual nights — e.g. a 3-night stay becomes `[2026-03-10, 2026-03-11, 2026-03-12]`.
2. **Acquire one Redis lock per night** — keys like `lock:property_42:2026-03-10`, each set with `SET key value NX EX <ttl>` (e.g. a 10-minute TTL matching the hold window). Each key's acquisition is atomic on its own.
   - **All locks acquired** → continue to step 3.
   - **Any lock already held** (another guest is mid-reservation for an overlapping night) → immediately release whichever locks *this* attempt did acquire, and return "unavailable for these dates" to the client. The database is never touched on this path — this is the cheap, sub-millisecond rejection that protects a hot property from a traffic spike.
3. **One database transaction**: `INSERT` a `booking_night` row per night (`property_id`, `stay_date`, `booking_id`) and the `booking` row itself (`status = PENDING`, `expires_at = now + hold TTL`, `idempotency_key`). The `(property_id, stay_date)` unique constraint is checked here too — in the normal case it never fires, since the Redis lock already excluded every other concurrent attempt; it exists for the case the lock can't cover (step 7). On success, the client gets back a `booking_id` and price — the hold is now live in *both* Redis (fast) and Postgres (durable).
4. **Client pays** — `POST /pay` with `booking_id` and an `idempotency_key`, routed to the Payment Service, which charges the external provider and waits on its webhook.
5. **On a successful payment webhook**, the Payment Service tells the Booking Service to confirm: flip `booking.status` from `PENDING` to `BOOKED`, then **release that stay's Redis locks** — the `booking_night` rows are now permanent proof of the booking, so the lock has done its job and can go.
6. **If payment never completes** (declined, abandoned, client disappears), two independent backstops reclaim the hold rather than relying on either alone: the **Redis lock's own TTL** simply expires, letting a fresh reservation attempt succeed immediately; separately, the **Hold Expiry Reaper**, sweeping the database continuously, finds `PENDING` bookings past their `expires_at`, deletes their `booking_night` rows, and defensively deletes the Redis key too in case the two TTLs ever drift apart (e.g. Redis was briefly unavailable when the lock should have been set).
7. **What happens if the lock layer is bypassed entirely** (a bug, a Redis outage, a client that skips straight to step 3) — if two such requests reach step 3 for the same night, only one `INSERT` succeeds; the other hits the `(property_id, stay_date)` unique-constraint violation and its whole transaction rolls back. The client-visible outcome is the same "unavailable for these dates" as step 2, just discovered slightly later and at the cost of one wasted DB round-trip — never a double booking.

The lock and the table are two layers of the same guarantee, not two competing ones: the **lock is where contention is normally resolved** — cheap and fast, keeping the database off the hot path — and the **constraint is where correctness is actually guaranteed**, the one thing still true no matter what Redis does.

### Search-index sync flow walkthrough (WAL → CDC → Elasticsearch)

A step-by-step trace of how a property write becomes searchable, without ever touching Elasticsearch synchronously:

1. **Property Write Service commits a change** — an `INSERT` or `UPDATE` on the `property` table (a new listing, a price change, a bulk-update row) — inside one local transaction against the Property DB Primary. That transaction knows nothing about search; it commits and returns exactly as it would with no search index at all.
2. **Debezium reads the database's write-ahead log (WAL) directly**, not the table. Every committed change already lands in the WAL as part of normal database durability, so Debezium sees it as a change event (with before/after images) **without adding any read or write load to the Property DB** — it's tailing a log the database was already writing.
3. **Debezium publishes the change event onto the Kafka CDC topic**, partitioned by `property_id` — so every change to one property is delivered to its consumer **in the same order it was committed**, even though changes to different properties may arrive interleaved.
4. **The Search Index Sync Worker consumes the topic** and turns each change event into an **upsert** (or a delete, for a removed listing) against the AWS Elasticsearch index, keyed by `property_id` — mapping the row's `city`, `nightly_price`, `description`, and amenities into the document shape Elasticsearch actually queries against.
5. **A failed upsert retries with backoff**; an event that keeps failing (a mapping error, a malformed row) goes to a dead-letter queue instead of blocking the consumer — so one bad property update can't stall every other property's sync behind it.
6. **Applying the same event twice is safe.** Kafka's at-least-once delivery means the worker may see a change event more than once; because each event is an upsert of the property's *current* field values (not a delta), replaying it just re-writes the same document. The one thing that does matter is **order** — replaying an *older* event after a newer one has already landed would regress the document — which is exactly what the `property_id`-partitioned topic guarantees against.
7. **This whole path is asynchronous and eventually consistent, on purpose.** A property update can take up to (and briefly beyond, under load) the requirements' 500ms SLA to appear in search — that's fine, because search is explicitly the **AP** side of this design: the Search Service's live availability check against the `booking_night` calendar (see the Ideal Architecture bullets above) is what actually gates a booking, so a momentarily stale search result can show an outdated price or description, but it can never cause a double booking.

**Why CDC over a synchronous dual write** (the Property Write Service calling both the DB and Elasticsearch directly): a dual write has a window where one call succeeds and the other fails, leaving the database and the search index permanently diverged with nothing to reconcile them. Reading the WAL means Debezium replays *every* committed change exactly as the database itself recorded it — there's no code path where a property write "succeeds" in the database but is silently never even attempted against search.

### Storage choices — which engine for which store

| Store | Category | Why this category, not another |
|---|---|---|
| `property`, `booking_night`, `booking`, `payment` | **Relational (PostgreSQL)** | The reservation write needs a multi-row **ACID transaction** across every night in a stay, plus a **unique constraint** on `booking_night(property_id, stay_date)` and foreign keys tying booking → payment. This is the one place correctness beats raw throughput, and the constraint — enforced by the database, not the app — is the mechanism that actually prevents overbooking. |
| Property/Booking detail cache | **In-memory KV, Redis, TTL + invalidate-on-write** | Sub-millisecond reads for a 100:1 read-heavy path; fully rebuildable from the relational store, so losing it costs latency, not correctness. |
| Reservation hold lock (`lock:{property_id}:{stay_date}`) | **Redis distributed lock, TTL-bound to the hold window** | Needs to reject contention in **sub-millisecond time, before the DB is touched** — exactly what a distributed lock is for. Deliberately not the source of truth: losing it (a Redis failover) only costs a slightly slower rejection path, never correctness, because the `booking_night` unique constraint is what actually guarantees no double booking. |
| Search candidates (`property` by city, price range, amenities, geo) | **Search index engine, AWS Elasticsearch** | Property search realistically needs more than city equality — geo-distance sorting ("near this landmark"), multi-attribute filtering (price range, guest count, amenities), and full-text on title/description, all with relevance ranking. That's Elasticsearch's actual shape; a plain key-value GSI would need bolt-on logic for each of these as the search feature grows. Sync via CDC (Debezium), never a synchronous dual-write, and treat it as a derived, read-optimized store — never the source of truth. |
| Property media (images/video, originals + renditions) | **Object storage, AWS S3** | Large, immutable blobs; served through a CDN, never through the app tier. |
| CDC events, media-pipeline tasks, bulk-update jobs | **Durable log, Kafka** | Decouples write throughput from downstream consumers (search-index sync, transcode workers, bulk-update apply) and makes each stage replayable. |

### Design trade-offs

- **Redis distributed lock for latency, DB unique constraint for correctness — both, matching the problem statement, not one instead of the other.** The lock does the job it's actually good at: reject a concurrent request in Redis, in sub-millisecond time, before it ever reaches the database — critical for shielding a hot property from the DB during a spike. The `INSERT` against a unique `(property_id, stay_date)` constraint inside one transaction is what actually *enforces* the invariant durably, because a lock can be lost (Redis failover), mistimed (TTL), or simply skipped by a bug — none of which are acceptable ways to lose a double-booking guarantee. Neither piece alone is the ideal design; running the lock with no durable backstop is what the original session got wrong, and skipping the lock entirely would give up the latency benefit the problem explicitly asked for.
- **Per-booked-night rows (sparse) over a whole-stay overlap row** — chosen because it turns the write into a plain unique-constrained `INSERT`, avoiding a range-exclusion constraint, and because only booked nights get a row at all (an open night simply has none), the table stays small regardless of catalog size. Trade-off: one `INSERT` per night written per booking, bounded by stay length (typically well under 14) and all inside one transaction.
- **Elasticsearch over a plain key-value index for search** — a hotel/property search realistically needs geo-distance sorting, multi-attribute filtering (price range, amenities, guest count), and full-text on title/description with relevance ranking — a DynamoDB GSI covers only exact-match filters and would need a bolt-on for each of the others as the feature grows. Elasticsearch stays a synced, read-optimized index (via CDC), never the write-of-record.
- **CP for booking/payment, AP for search/browse, stated explicitly** — a stale search result is corrected by the live availability check at reservation time; a stale booking or payment is never acceptable.
- **Two independent expiry paths, not one** — the Redis lock's own TTL and the DB-driven `Hold Expiry Reaper` both release an abandoned hold, so neither Redis losing the lock nor the reaper being delayed can leave a night stuck.

### Logging, Monitoring & Alerts

| Signal | Alert threshold | Why it matters |
|---|---|---|
| **Redis lock acquisition failure rate**, per property | Sustained spike on a single `property_id` | Signals a flash-sale-style hot property that needs gateway-level queueing, not a generic capacity problem — this is the fast signal, ahead of any DB-side conflict |
| **`booking_night` unique-constraint conflict rate** | Any sustained non-zero rate | Should be near zero given the Redis lock catches contention first; a sustained rate here means the lock is being bypassed or is out of sync with the database and needs investigating |
| **Hold Expiry Reaper backlog** | Backlog growing rather than draining | Held nights aren't being released — inventory is silently locking out real availability |
| **CDC / search-index sync lag** | > 500ms (the stated SLA) | The one number the original requirements named as an SLA with no metric behind it |
| **Property/Booking cache hit ratio** | Sustained drop | Signals a cache stampede or a bad invalidation, usually right after a bulk update |
| **Payment webhook duplicate/failure rate** | Spike over baseline | Signals a provider issue or a replay, caught by the idempotency-key dedup before it becomes a double charge |
| **Transcode pipeline DLQ depth** | > 0 for more than a few minutes | A permanently stuck media task that will otherwise disappear silently |
| **Bulk-update cache-invalidation queue depth** | Growing during a bulk job | The thundering-herd signal a large bulk update would otherwise cause on `Property Cache` |

## Takeaways to drill

1. **Use the Redis distributed lock and the DB unique constraint together, not the lock alone.** The problem statement's two-step `reserve`/`confirm` flow with a Redis TTL hold is the right shape — but a lock by itself can be lost, mistimed, or skipped, so pair it with a durable `(property_id, stay_date)` unique constraint that's the actual source of truth. The lock buys latency; the constraint buys correctness. Neither substitutes for the other.
2. **Wire search to filter on live availability before returning a result** — a property that looks bookable but isn't is a functional bug, not an edge case.
3. **Match the search backing store to the actual query shape and say so out loud** — a property search that needs geo-distance, multi-attribute filters, and full-text ranking earns Elasticsearch's complexity; a pure equality lookup wouldn't. Name which one your search actually needs, and why.
4. **Every hold needs a durable, DB-backed expiry path**, not just a cache TTL — a TTL-only hold doesn't survive a restart.
5. **Idempotency keys belong on every retriable write** (reserve, pay, webhook) — this is now a repeat item across multiple sessions in this tracker.
6. **Size the hot key** (concurrent reservation attempts on one popular property/date), not just the aggregate write QPS — it's the number that decides whether the gateway needs per-property throttling.
7. **A bulk-write requirement needs its own architecture path** — batched/async with rate-limited cache invalidation — not just a line in the requirements.
8. **Name monitoring signals concretely** — conflict rate, reaper backlog, replication lag, DLQ depth — "add monitoring" on its own isn't a design.
